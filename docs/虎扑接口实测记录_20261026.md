## 五、★ 选手评分接口（2026-10-26 20:20 已锁定，免登录）

### 5.1 实际可用的 base


### 5.2 两个端点

**(A) 反查节点（选手 → 所属局）**

```
GET /bpl/score_tree/getSelfByBizKey?outBizType={type}&outBizNo={no}
```

返回 `data.nodeId`、`data.linkNodes[]`，其中含父级节点，例如：

```jsonc

  "outBizKey": { "outBizType": "lol_bo", "outBizNo": "7717", "key": "lol_bo:7717" }

```

**(B) 取子节点评分（局 → 全阵容）**

```
GET /bpl/score_tree/getCurAndSubNodeByBizKey
```

### 5.4 完整解析链路

```
评分页 URL
  → outBizType=lol_item & outBizNo=79822
  → (A) getSelfByBizKey  → linkNodes 里找到 lol_bo:7717
```

## 六、★ 赛程接口（2026-10-26 21:20 打通）

### 6.1 树结构与关键结论

```
lol:1（根：英雄联盟赛事，nodeId=1458935，subNodeCount=0）
└── lol_match（比赛，如 "HLE 0-1 IG"，bizId=4513）
    └── lol_bo（第1局，bizId=7717）
        └── lol_item（选手/教练/BP英雄/解说，bizId=79822）
```

向上取父节点：
```
GET /bpl/score_tree/getCurAndSubNodeByBizKey?relation=PARENT&outBizType=lol_match&outBizNo=4513
→ pageResult.data[0].node = 「英雄联盟赛事」 lol:1
```

**但根节点没有子节点**：
- `getCurAndSubNodeByBizKey(relation=CHILD, lol:1)` → `pageResult` 空、`totalCount=0`
- `groupAndSubNodes(nodeId=1458935)` → `nodePageResult.totalCount=0`
- `getSubGroups(outBizType=lol&outBizNo=1)` → `data={}`
- `lol_competition` / `lol_season` / `lol_tournament` + `competitionType=130159678583195` / `competitionStageType=110469977` → **全部不存在**

⇒ **无法通过父节点列出比赛**，只能按 `bizId` 枚举。

### 6.2 编号规律：赛事内连续

实测扫描（`getSelfByBizKey?outBizType=lol_match`）：

| bizId | 比赛 | 赛事 | 状态 |
|---|---|---|---|
| 4501–4516 | 全部有效，共 **16 场连续** | 全球总决赛 | COMPLETED |
| 4500 / 4517 | 空 | — | — |
| 3400 | KT 2-0 KRX | LCK联赛 | COMPLETED |
| 2800 | G2 1-0 FUR | 电竞世界杯 | COMPLETED |
| 2000 / 1200 / 600 / 100 | 空 | — | — |

**⇒ 同一赛事内 id 连续，赛事之间有空档（可能是几百到上千）。**

### 6.3 单场字段（detail.infoJson）

| 需求 | 字段 |
|---|---|
| 队名 | `homeTeamName[0]` / `awayTeamName[0]` |
| 比分 | `homeTeamScore[0]` / `awayTeamScore[0]` |
| 队标 | `homeTeamLogo[0]` / `awayTeamLogo[0]` |
| 赛事名 | `competitionTypeCn[0]`（如「全球总决赛」） |
| 阶段 | `competitionStageTypeCn[0]` |
| 比赛时间 | `matchTime[0]`（unix 秒） |
| 状态 | `matchStatus[0]`（COMPLETED / …） |
| 胜方 | `winTeamId[0]`（与 homeTeamId / awayTeamId 比较） |
| 官方 match id | `matchId[0]` |

### 6.4 App 采用的发现策略（`HupuMatchService.discover`）

```
1. 锚点（默认 4516，最新一场）有效 → 直接用
   无效 → 上下各按步长 8 粗扫 10 轮，找任一可用锚点
2. 从锚点向两侧逐号探测
3. 单向连续 3 次未命中即停（单向上限 40 次）
4. 按 matchTime 倒序返回
```

**已知局限**：跨赛事空档较大时，粗扫可能找不到下一个区块（step=8 会跳过窄区块）。
后续若要更稳，可改为「记录上次的 maxId 到本地，下次从该点向上探」。

### 6.5 局列表与选手评分

```
GET /bpl/score_tree/getCurAndSubNodeByBizKey?relation=CHILD&outBizType=lol_match&outBizNo=4513
→ 局列表（lol_bo，name 如「第1局」）

GET /bpl/score_tree/getCurAndSubNodeByBizKey?relation=CHILD&outBizType=lol_bo&outBizNo=7717
→ 选手/教练评分（同第五节的 24 条结构）
```

### 6.6 坑：成功码是 1，不是 200

`games.mobileapi.hupu.com/bplcommentapi/*` 成功返回 `{"code":1,"msg":"成功"}`，失败为 `code:-1`；
而 `bbs.hupu.com/api/v2/*` 用的是 `code:200`。
`HupuClient.getJson` 因此增加 `okCodes` 参数（默认 `{200}`，评分/赛程调用传 `{1}`）。

## 七、评论接口（2026-10-26 21:45 打通）

```
GET /bplcommentapi/bpl/comment/list
    ?outBizType=lol_item&outBizNo=79822&publishTime=0&order=HOT&page=1&pageSize=20
```

**参数**（缺一个就报错，报错信息会明确点名缺哪个字段）：

| 参数 | 说明 |
|---|---|
| `outBizType` / `outBizNo` | 评分对象；**只有 `lol_item`（选手）有数据** |
| `publishTime` | 必填，传 `0` 即可（传节点发布时间也行） |
| `order` | 必填，界面上的「最亮/最晚/最早」；传 `HOT` / `NEW` 均可 |
| `page` / `pageSize` | 分页 |
| `cursor` | 响应里带，可用于游标翻页 |

**响应**：`data.comments[]` / `data.commentCount` / `data.hasMore` / `data.cursor`

**评论字段**（节选）：

| 字段 | 说明 |
|---|---|
| `commentUserName` / `commentUserHeadImg` | 用户名 / 头像 |
| `commentContent` | 正文 |
| `commentContentImages` | 配图，可能为 null / 字符串数组 / 对象数组 |
| `commentDate` | 「20小时前」这类相对时间 |
| `lightCount` | 亮数 |
| `score` | 该用户给这个选手打的分（0 = 未打分） |
| `ipLocation` | 省份 |
| `commentOccasionText` | 例如「发布于比赛中」 |
| `subCommentCount` | 子回复数 |

### 7.1 关键结论：评论挂在选手上，不在比赛上

| 节点 | commentCount |
|---|---|
| `lol_match:4513`（比赛） | **0** |
| `lol_bo:7717`（第1局） | **0** |
| `lol_item:79822`（Gumayusi） | **4688** |

⇒「每场比赛的评论」实际要按**选手**拉取值，App 里做成「点选手卡片 → 弹出评论区」。

### 7.2 队伍 id → 队名

选手节点的 `infoJson.teamId` 是虎扑内部队伍 id（如 `137`、`1693079573970944`），
**没有队名字段**。队名要从**比赛节点**的 `homeTeamId/homeTeamName`、`awayTeamId/awayTeamName` 映射：

```dart
if (teamId == match.homeTeamId) name = match.homeTeam;
else if (teamId == match.awayTeamId) name = match.awayTeam;
```

### 7.3 ⚠️ 更正：评论的正确接口与排序

第七节开头写的 `bpl/comment/list` **不是评论列表页用的接口**——它固定返回 10 条、忽略排序参数。
真正的前端调用在 chunk `8402.4afb81ca.js` 里：

```js
// 排序选项（原样摘录）
[{label:"最亮", value:"brightest"}, {label:"最晚", value:"latest"}, {label:"最早", value:"earliest"}]
map = { earliest: "asc", latest: "desc", brightest: "" }
```

对应三个真实调用：

| Tab | 端点 | 关键参数 | 实测 |
|---|---|---|---|
| **最亮** | `GET bpl/comment/list/primarySingleRow/hottest` | `outBizType` `outBizNo` `clientCode=` `cid=` | **返回裸数组 50 条**，按亮数降序（8513 → 11） |
| 最晚 | `GET bpl/comment/list/primarySingleRow` | `order=desc` + `publishTime=<当前时间 ms>` | 10 条/页 |
| 最早 | `GET bpl/comment/list/primarySingleRow` | `order=asc` + `publishTime=0` | 10 条/页 |

**翻页**：响应里的 `data.cursor = {publishTime: <long>, limit: 10}`，
把该 `publishTime` 作为下一轮的 `publishTime` 传回即可（`page` 参数无效）。

**坑**：
- `order` 传 `HOT`/`NEW`/`LIGHT` 都不会报错，但**服务端忽略**，永远返回同一批 → 看起来"最亮/最新没区别"
- `order=desc` 若 `publishTime=0` 会**返回空**（desc 从"当前时间"往回翻，0 太早）
- `getMore` 是**子回复**接口（需 `parentCommentId`），不是主列表翻页

## 十、楼中楼（子回复）接口（2026-10-26 22:15 打通）

### 10.1 结论：用 `getMore`，不是 `subCommentList`

| 端点 | 结果 |
|---|---|
| `primarySingleRow/subCommentList` | **`data: null`**（各种参数组合都试过，包括真实 publishTime） |
| `primarySingleRow/getMore` | ✅ 正确返回子回复 |

```
GET /bplcommentapi/bpl/comment/list/primarySingleRow/getMore
    ?publishTime=<父评论的 publishTime（翻页时用上一页 cursor）>
    &outBizNo=<选手 bizId>
    &outBizType=lol_item
    &queryType=asc
    &parentCommentId=<父评论 commentId>
    &pageSize=20
    &clientCode=&cid=
```

响应结构与主列表一致：`data.comments[]` / `data.cursor` / `data.commentCount` / `data.hasMore`。

### 10.2 为什么重要

实测「最亮」50 条主评论里，**33 条带子回复**（最多的 63 条）——
不展示楼中楼会漏掉绝大部分评论，与虎扑 App 差距明显。

| 主评论 | 亮数 | 子回复数 |
|---|---|---|
| 对位领先你的钱够去商城买个新英雄 | 8513 | **49** |
| 温馨提示：再输一把就要回家了喔 | 3063 | **45** |
| 哎，你怎么现在就犯病了？ | 1028 | **63** |

### 10.3 App 实现

- `HupuComment` 增加 `subCount`（来自 `subCommentCount`/`descendantCount`）与 `publishTime`
- `HupuMatchService.fetchSubComments(...)` 走 `getMore`
- 评论卡片：`subCount > 0` 时显示「查看 N 条回复」→ 展开为左侧竖线的紧凑子回复列表，
  底部「加载更多回复」按 `cursor.publishTime` 翻页，可再次点击收起

## 十一、两处导致「有评分却显示暂无评分」的坑（2026-10-27 修复）

### 11.1 比赛编号是**分簇**的，不是一路递增

实测（2026-10-27 07:50）：

| 号段 | 覆盖日期 | 说明 |
|---|---|---|
| 4501–4516 | 10-18 ~ 10-26 | 第一簇（原有） |
| **4517–4600** | — | **全空**（383 个空号） |
| 4601–4610 | 10-24 ~ 10-27 | **第二簇（新开）** |
| 4440–4500 | — | 全空 |

原来的发现算法是「从 seed=4516 逐号 ±1，连续 3 次未命中就停」——
从 4516 走到 4517/4518/4519 三次未命中即停，**永远到不了 4601**，
于是 10-27 新打完的 4 场（CFO 0-1 T1、BLG 1-0 KC、LOS 2-0 TSW、TLAW 2-0 AL）全部没有评分。

**新算法**（`HupuMatchService.discover`）：

```
首次：步长 10 网格扫描 [seed-40, seed+400]（45 探）
    + 步长 50 稀疏远扫 [seed+400, seed+2400]（40 探，防跨簇跳跃）
    + 每个命中点向两侧 ±12 展开补齐整簇
之后：内存缓存增量（从已知最大号 +40 / -10），刷新 1~2 秒
全程 10 路并发
```

### 11.2 队名写法不一致

| 队伍 | LPL 官方 | 虎扑 | 结果 |
|---|---|---|---|
| KOI | `MKOI` | `KOI` | 直接比字符串 ✗ |
| TL | `TLAW` | `TL` | 直接比字符串 ✗ |

影响 6 场比赛（10-24、10-25、10-26、10-27 各一到两场）。

**修复**：`core/team_alias.dart`

```dart
const _alias = {
  'MKOI': 'KOI',  'MOVISTAR KOI': 'KOI',
  'TLAW': 'TL',   'TEAM LIQUID': 'TL',
  'FURIA': 'FUR', 'FURIA ESPORTS': 'FUR',
};
String canonicalTeam(String raw);  // 去空格 + 大写 + 别名
```

`LplMatch.joinKey` 与 `schedule_page._hupuKey` 都走同一套归一化。

### 11.3 修复后的匹配率

| | 修复前 | 修复后 |
|---|---|---|
| 匹配成功 | 20 / 30 | **26 / 30** |
| 剩余「暂无评分」 | 10 场 | 4 场 |

剩余 4 场是 **10-16 / 10-17 入围赛**（C9/KC、FUR/MVK、KC/MVK、C9/FUR）——
实测扫遍 4440–4620 都没有对应节点，**虎扑就没建这几场的评分**，属正常。

| 采样 | 结果 |

### 12.3 最终方案（App 已改为）

